     `onClick={() => navigate('/app/vex')}`

     The `GET /api/vex` endpoint parses `job_id`, `cve_id`, `status`, and `source_type`.
     It DOES NOT accept or filter by a `date` parameter.

2. Why the Report Was "Recycled Mock Data" Overwriting Old Records:
   - File: `backend/pipeline/vex_generator.py` (Lines 384-498 in `generate_vex_documents_for_runtime`):
     A. Job ID Hijacking:
        Line 385: `latest_job = Job.query.order_by(db.desc(Job.submitted_at)).first()`
        Instead of creating or linking to a dedicated runtime telemetry job for that date,
        it hijacked the latest uploaded scan job ID (`ZX-F90F0CAE`, which was an SBOM scan!).
     B. Row Overwriting Bug:
        Line 417: `cve_id = item.matched_cve_id or item.finding_category or "INVENTORY_DRIFT"`
        Line 462-465:
        `existing_doc = VexDocument.query.filter_by(job_id=target_job_id, cve_id=cve_id).first()`
        Because all drift findings share the generic `cve_id = "INVENTORY_DRIFT"`, the database
        lookup matched the EXACT SAME pre-existing VEX row (originally seeded from August 23, 2026,
        VEX ID `VEX-RT-20260823-E9D3E5`).
     C. Timestamp Mutation:
        Lines 470-476:
        ```python
        if existing_doc:
            existing_doc.status = vex_status
            existing_doc.justification = justification
            existing_doc.evidence_summary = evidence_summary
            existing_doc.cyclonedx_vex_json = doc_json
            existing_doc.signature = signature_b64
            existing_doc.signature_timestamp = now_time
            existing_doc.generated_at = now_time   # <--- MUTATING OLD RECORD TIMESTAMP

        ```
        Instead of creating new VEX documents scoped to the 2026-09-05 findings, it merely updated
        the `generated_at` timestamp on the old row to the current second (`Sep 08, 2026, 09:06:23 AM`).
        This is why the VEX ID retained the old date prefix `VEX-RT-20260823-...` while the GENERATED
        column displayed `Sep 08, 2026`.

3. Why Findings Showed 5 Findings But The Banner Said 23 Records:
   - On date `2026-09-05`, the SQLite database table `runtime_inventory` contains 23 records.
   - 18 of those records have `finding_category = 'DECLARED'` (normal system processes/OS DLLs).
   - Only 5 records have `finding_category = 'INVENTORY_DRIFT'` (active runtime processes absent

       2) updater.exe (PID 16092)
       3) MpCmdRun.exe (PID 15312)
       4) Integrator.exe (PID 24652)
       5) TrustedInstaller.exe (PID 23208)
   - In `backend/api/jobs.py` (Lines 669-703), the Findings page filters for actual security findings
     (`INVENTORY_DRIFT` or `UNKNOWN_RUNTIME_COMPONENT`), correctly displaying 5 items.
   - However, in `backend/pipeline/vex_generator.py` (Line 409-416), the generator looped through
     ALL 23 inventory rows, including the 18 normal declared items!
   - In the loop, all 18 declared items matched the single row `cve_id = 'DECLARED'` and all 5 drift items
     matched the single row `cve_id = 'INVENTORY_DRIFT'`. The code appended `existing_doc` to `created_docs`
     23 times, falsely reporting `23 VEX Compliance records created` when in reality only 2 rows were
